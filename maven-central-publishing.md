# Publishing to Maven Central

Read before any `deploy` to Maven Central, and before planning a release. One copy of the truth: the limits section below replaced an older note (2026-10-01) that gave stricter per-file limits and said snapshots belonged on GitHub releases. Both were superseded by Sonatype's answer of 2026-10-12.

## Maven 4 for day-to-day work, Maven 3 for `deploy`

- **MAVEN CENTRAL PUBLISHING — DO NOT USE MAVEN 4.0.0-rc-5 FOR `deploy`, USE AN OLDER STABLE MAVEN 3 INSTALL.** `org.sonatype.central:central-publishing-maven-plugin` (both 0.6.0 and 0.9.0) breaks under Maven 4.0.0-rc-5's new named-locks concurrency feature: it bundles a stray `.locks` directory into the upload, and Central rejects the whole bundle ("Bundle has content that does NOT have a .pom file: .locks"). There is a documented workaround (`-Daether.syncContext.named.factory=noop`), but the simpler fix is to just not use Maven 4 for this: run a plain, unpatched Maven 3.9.x (`mvn.cmd clean deploy -Dorg.name=<org>`) and no workaround flag is needed at all. Confirmed working end-to-end 2026-09-11 publishing all 6 first-release artifacts of the `datapotter` org.
- **THE RULE IN ONE LINE: MAVEN 4 FOR DAY-TO-DAY WORK, MAVEN 3 FOR `deploy` TO MAVEN CENTRAL.** Maven 4.0.0-rc-5 is correct for compile, test, package, install and everything else — it is faster and it is what the projects are developed against. The ONLY thing it must not do is publish. For that, always Maven 3's `mvn.cmd clean deploy -Dorg.name=<org>`.
- **AND THERE IS A SECOND, SILENT MAVEN 4 FAILURE — WORSE THAN THE `.locks` ONE ABOVE, BECAUSE NOTHING GOES WRONG ON SCREEN.** Observed 2026-09-15 releasing `datapotter` 2.0. Under Maven 4 the `central-publishing-maven-plugin`'s `<extensions>true</extensions>` lifecycle binding does not take effect at all, so the `publish` goal NEVER RUNS: `gpg:sign` and `install:install` execute, the reactor prints **BUILD SUCCESS**, the exit code is 0, and not one byte is uploaded. There is no `.locks` error because no bundle is ever built. The `.locks` case above is the one where the plugin DID run; this is the one where it did not. **So never treat BUILD SUCCESS as evidence that a release happened.** Confirm a publish two ways: the plugin must print `central-publishing:<ver>:publish` per artifact plus `Uploaded bundle successfully, deploymentId: <uuid>` and `was successfully published`, and then the artifact must actually fetch from `https://repo1.maven.org/maven2/io/github/<org>/<artifact>/<version>/`. Propagation to repo1 lags the portal by roughly ten to thirty minutes, so a 404 immediately after a publish is normal and is not itself a failure — the portal's "was successfully published" line is the authoritative signal, and repo1 is the confirmation once it catches up.
- **A REACTOR PARENT POM IS ITSELF A PUBLISHED ARTIFACT, AND IS EASY TO FORGET.** Every module names it in `<parent>`, so if it is not on Central nothing in that reactor resolves. It therefore needs the full set — `url`, `licenses`, `developers`, `scm` — plus the gpg and central-publishing plugins, exactly like the modules. Miss it and `deploy` falls through to `maven-deploy-plugin`, which dies on `repository element was not specified in the POM inside distributionManagement`, killing the reactor before a single module uploads. This stays hidden for as long as the modules are versioned independently with no shared parent; it appears the moment a reactor is consolidated onto one version line. Hit on both `datapotter/datahelper` and `datapotter/arcadedbhelper`, 2026-09-15. Related: Central also rejects any release whose dependencies include a `-SNAPSHOT`, so a downstream reactor can only be published after the core it consumes has been.

## Limits, snapshots, and one upload per release

- *Scope — any PUBLIC Java/Maven project published to Maven Central (orgs jarrunner, xyz-jphil, luvml, datapotter, and any added later); private projects are never published and stay local :* **Snapshots freely, releases rarely, and one upload per release.** Get the latest code to people as `X.Y.Z-SNAPSHOT` on Central's snapshot repository (`https://central.sonatype.com/repository/maven-snapshots/`, enabled per namespace in the Portal). **Sonatype confirmed on 2026-10-12 (ticket #128502) that snapshots do not count towards the usage limits.** Releases do: limits are per organisation per month (release size, file count, release count; enforced since 2026-10-01; over a limit, a 30-day grace period, then refused). The default is about 80 MB, 1,000 files and 7 releases. An open-source project can ask central-support for an OSS exemption: jarrunner got one, raising its size limit to 150 MB, but the release count stayed at 7. **A release is one upload (one Portal deployment), however many artifacts it carries**, so pending artifacts across several repos go out together in one bundle: one release instead of four. Keep two releases a month in hand for an urgent fix. There is no API for the limits; read the usage before each release (jarrunner's script works for any org). Never pin a pom to a version that exists only in one machine's `~/.m2`: it must be on Central or deployed to the snapshot repository. Consumers add that repository once per machine in `~/.m2/settings.xml`, as both `<repository>` and `<pluginRepository>`. Still publish snapshots when there is something to publish, not from every CI build: Sonatype's own guidance asks publishers to "avoid publishing every CI build". Recorded 2026-10-10 after the jarrunner organisation went to 129% of its release-size limit with one 92 MB release and 60 poms were found pinned to a plugin SNAPSHOT that existed only locally; updated 2026-10-12 with Sonatype's answer and the first combined release. Lessons from that release, each hit once: (i) the one-upload rule was measured, not assumed: 4 releases before, 5 after an upload of four packages; (ii) an OSS exemption shows in the usage endpoint as a NAMESPACE override (`namespaceMetrics[].ownLimit`), while the top-level `limit` keeps the global default, so a script reading only the top level reports the old limit; (iii) `-DskipPublishing=true` signs everything but leaves central-publishing's bundle empty, so a combined upload is assembled by hand and posted to the Portal API; (iv) before a plugin or library that bundles a pre-release goes to Central, release the final version of what it bundles first, because a Central release can never be changed afterwards; (v) after moving consumers to a release, also remove the snapshot repository entries that existed only for those snapshots, and prove the build from a clean CI runner, not from this machine's ~/.m2.
- A fat shaded jar (several of ours are 85-240 MB) can exceed a month's size limit on its own, so it should normally go to GitHub releases (jr's `run.url` + sha256 exists for exactly this), with only the thin library jar on Central.
