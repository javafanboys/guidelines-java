# Resident Java apps: RAM, GC and memory flags

Read before building anything that stays running (tray, daemon, gate, resident server). The GC section applies to every jr app, resident or CLI.

## RAM POLICY FOR RESIDENT JAVA APPS (trays, daemons, gates — anything that stays running)

- **The rule: a spike is fine, an idle app must give memory back.** Several of these run all day (cdpgate, gitgate, sshgate, a credential wallet, proj's daemon); each one sitting idle on a default JVM holds 140-180 MB of RAM and 250-450 MB committed. Measured 2026-10-20: cdpgate 148 MB, gitgate 177 MB, a credential wallet 141 MB working set, ~950 MB committed between them, all doing nothing.
- The collector and the flags are in the next section, GARBAGE COLLECTOR AND MEMORY FLAGS.
- **The idle trim, which is where most of the saving is:** after N minutes with no work (2 is a good default), call `System.gc()` once, then on Windows `SetProcessWorkingSetSize(GetCurrentProcess(), -1, -1)` (or psapi `EmptyWorkingSet`): the committed pages are moved out of RAM, and come back in milliseconds when the app next does something. Once per idle stretch, never in a loop. Measured on the three apps above: 148 / 177 / 141 MB → 3 / 7 / 3 MB. Ready to use: `leasegate.core.IdleTrim.start(name, () -> lastActivity, Duration.ofMinutes(2))` in `io.github.leasegate:leasegate-core` (public, no UI); a private project may depend on it.
- **Measure before and after, never assume:** PowerShell `Get-Process <name> | Select WorkingSet64, PrivateMemorySize64`. Working set is what is in RAM now; private bytes is what is committed. Watch it again a minute later: a UI that redraws something every second (a tray tooltip ticker) pulls pages back in, so such tickers should run only while a window is open.
- **In JavaFX, never poll with an endless `Timeline` (`setCycleCount(INDEFINITE)`) in a resident app.** While any animation runs, JavaFX keeps its frame clock ticking about 60 times a second, so the idle process keeps pulling its pages back in. Seen 2026-10-20 in a credential-wallet tray app: 16 MB right after the idle trim, 55 MB a minute later, from a 5-second tray-state poll and a 60-second health tick. Poll from a daemon `ScheduledExecutorService` and `Platform.runLater` only when something changed. A countdown `Timeline` inside a window is fine if `setOnHidden` stops it.
- **Measured 2026-10-24 on proj's and jacli's daemons (littlejlib/proj PRP 42, littlejlib/jacli PRP 07): 543 MB -> 13 MB and 806 MB -> 25 MB in RAM when idle. What each step was worth, and the traps:**
	- **Two-stage trim.** A daemon several claude sessions use gets a request every few minutes, so a 2-minute idle timer never fires (jacli sat at 300 MB with a 70 MB heap). Stage one, after ~15 quiet seconds: `SetProcessWorkingSetSize(-1,-1)` only, which is nearly free. Stage two, after ~2 minutes: `System.gc()` and release caches, then page out. Ready code: `daemon/IdleTrim` in `littlejlib/proj` and in `littlejlib/jacli`.
	- **"Activity" must include the app's own background work** (a watcher batch, a reindex, a periodic walk), or the trim runs just before it and never after. It must NOT include a periodic check that does nothing, or the trim recurs every tick.
	- **Measure what each periodic tick allocates.** proj's 5-minute tick asked the index when a group was last scanned, and that one query pulled 150-200 MB back into RAM every time. Keep such an answer in memory.
	- **Default initial heap is 1/64 of RAM** (252 MB committed on this 16 GB machine): always `-Xms16m`. A daemon also wants `-XX:MaxNewSize=48m`, so a burst of allocation cannot re-inflate the working set.
	- **Embedded ArcadeDB's page cache defaults to a quarter of the max heap** (jacli held ~280 MB of 64 KB page buffers). Set `GlobalConfiguration.MAX_PAGE_RAM` (jacli: 48) or use the `low-ram` profile (proj does).
	- **Every `WatchService` key holds a 16 KB native buffer** (15,459 keys were ~250 MB). On Windows register one key per root with `ExtendedWatchEventModifier.FILE_TREE` and cut the events yourself (ignored folders, depth, nothing below a leaf project); elsewhere stop descending where the scanner would. A build writing `target/` touches its parent's listing, so filter those events before doing any work.
	- **A daemon the app starts itself must be the same jr exe, not `java -jar`**, or Task Manager shows `java`. The exe path is the property `io.github.jarrunner.jr.exe`, the baked VM args are `io.github.jarrunner.jr.jvm.vmArgs.N`, and a per-launch override is `-Xjr:vm.args=<all args as one string>`. Do not use `JDK_JAVA_OPTIONS`: every terminal the daemon opens inherits it.
	- **Measure by PID** (`Get-Process -Id`): matching on the name picks up other sessions' short-lived `proj` runs. Tools that worked: `jcmd <pid> VM.native_memory summary` (start with `-XX:NativeMemoryTracking=summary` via `JDK_JAVA_OPTIONS` for the test only), `jcmd <pid> GC.class_histogram` (it forces a GC, so it shows what is live), `jcmd <pid> JFR.start duration=240s` then `jfr print --events jdk.ObjectAllocationSample` summed by thread (one sample's weight is an estimate and can be absurd; sum, do not trust a single line), and trimming the process from outside with `SetProcessWorkingSetSize` to tell "something keeps touching memory" from "the in-process trim did not run".
	- **Derived, read-mostly data (an index) does not need a database.** jacli's ArcadeDB index became one pack file per project (sorted string pool, flat int tables, binary search in place): query 16-43 ms instead of 190-300 ms, jar 9 MB instead of 70, and a rebuilt project cannot damage another.

## GARBAGE COLLECTOR AND MEMORY FLAGS (every jr app, resident or CLI) — measured 2026-10-20 on bwgate, JDK 25 and JDK 27

- **Every jr app names its collector in `vmArgs`.** From JDK 27 (JEP 523) a JVM that names none gets plain G1 on every machine, and plain G1 is the one setting we never want.
- **Serial is the default, because nearly every app of ours is small** (little live data: trays, gates, CLIs, recorders). It is the smallest on JDK 25 and JDK 27 alike, and JEP 523 itself says to keep choosing Serial explicitly where it performs best. It is not deprecated; the JEP lists removing any collector as a non-goal.
	- tray / UI app: `-Xms16m -Xmx96m -Xss512k -XX:+UseSerialGC -XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=30 -XX:TieredStopAtLevel=1 -XX:MaxMetaspaceSize=96m -XX:ReservedCodeCacheSize=32m -XX:MaxDirectMemorySize=32m` (raise `-Xmx` if messages can be large, e.g. cdpgate 512m; a cap costs nothing until used)
	- short-lived CLI: `-Xms8m -Xmx64m -Xss512k -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -XX:ReservedCodeCacheSize=24m`
- **G1 only for apps that embed ArcadeDB or hold a real heap** (an indexer, a large cache), and then ALWAYS with its three caps: `-XX:+UseG1GC -XX:ParallelGCThreads=2 -XX:ConcGCThreads=1 -XX:MarkStackSize=64K`, plus `-Xms16m`, an `-Xmx` cap, `-XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=30` and the idle trim. Do not add `G1PeriodicGCInterval` alongside the idle trim: in an idle app it collects every few minutes and pulls the trimmed pages back into RAM.
- **Never plain G1 in an app of ours.** On this 16-core machine it gives itself 13 parallel + 3 concurrent workers and a 32 MB marking stack (`MarkStackSize=4M` entries, sized for any heap, never used by a small one). Its own bookkeeping, NMT category "GC": **59 MB** plain, 37 MB with the thread caps, **~6 MB** with all three caps, Serial 0.1 MB. A small starting mark stack is safe: G1 grows it if marking ever overflows.
- **The measurement (bwgate, 96 MB heap, same jar and flags, only the collector changed; MB):**
	- committed after the idle trim — JDK 25: Serial 183, plain G1 244 · JDK 27: Serial 189, plain G1 245, tuned G1 189
	- RAM a minute after the idle trim — JDK 27: Serial 20.7, tuned G1 21.3, plain G1 24.4 (JDK 25 within a few MB of these)
	- threads — Serial 56, tuned G1 62, plain G1 76
	- G1 also grows the heap further while working (48 MB against Serial's 25); the idle trim takes it back.
- **JDK 27 is no game changer for us; stay on JDK 25.** JDK 27 only defers committing the marking stack until the first marking cycle: an empty JVM probe shows plain G1's overhead falling from 62 to 14 MB, but a real app reaches a marking cycle within minutes and is back at 59 MB. Tuned G1 matches Serial at rest on either JDK, so it is also the fallback if Serial is ever retired: one flag per pom.
- **How to check an app:** `jcmd <pid> VM.flags` (which collector, `MarkStackSize`), `jcmd <pid> GC.heap_info` (live heap), and for the GC's own memory start it with `-XX:NativeMemoryTracking=summary` then `jcmd <pid> VM.native_memory summary`. A JVM that only runs `-version` with `-XX:+PrintNMTStatistics` is a quick probe, but it hides costs that appear only once the app has run for a while (the JDK 27 mark stack above).
