TeaVM C-backend gotchas — maintained notes, not a tutorial. Read this before touching TeaVM's C target for anything beyond a toy. Discovered the hard way in `littlejlib/jr` PRP-07 (2026-09-11); jr's `teavm-poc/` folder is the worked, verified reference implementation — `postprocess.ps1` there is the actual patch script, copy it rather than re-deriving these fixes from scratch.

## Toolchain: use llvm-mingw, not tcc
- **tcc (Tiny C Compiler) does NOT pair with TeaVM's C backend — do not retry this without a good reason.** TeaVM lays out one `.c`/`.h` pair per Java class and nested classes reach shared headers via relative paths like `../../../core.h`. tcc resolves quoted includes by literal string concatenation of the path used to reach the current file rather than a canonicalized directory, so the SAME physical header gets reached via two different literal path strings in one translation unit, and tcc's `#pragma once` keys off the literal string — it doesn't recognize them as the same file and re-expands a struct body, producing `error: incompatible redefinition of 'TeaVM_FieldDescriptor'`. Real fix would mean rewriting every generated `#pragma once` into a traditional `#ifndef X_H` guard (immune to this because the guard identity is the macro name, not the path string) — not attempted; tcc 0.9.27 was tried and abandoned for this reason, not a preference.
- **llvm-mingw works.** Use the **msvcrt** variant (not ucrt) if avoiding a vcredist dependency matters — msvcrt is the legacy, always-present-on-Windows CRT; ucrt is technically also an OS component since Win10 but pulls in more mismatches (see below). Official releases: https://github.com/mstorsjo/llvm-mingw/releases — grab `llvm-mingw-<date>-msvcrt-x86_64.zip`.

## Driving TeaVM's C backend — skip teavm-cli, use the tooling API directly
- **`org.teavm:teavm-cli` is unreliable — don't reach for it.** It was not published to Maven Central for 0.15.0 (only core/classlib/tooling were — check via a direct 404 on repo1.maven.org before assuming a version has it). Even at 0.14.1 its shaded `-all.jar` throws `NoClassDefFoundError: org/apache/commons/cli/ParseException` on the bare `--help` invocation — commons-cli got relocated to `org.teavm.apachecommons.cli` inside the jar but something still references the unrelocated package.
- Drive `org.teavm.tooling.TeaVMTool` directly instead (`setTargetType(TeaVMTargetType.C)`, `setClassPath(...)`, `setMainClass(...)`, `setTargetDirectory(...)`, `.generate()`) — this is exactly what teavm-cli's `TeaVMCBuilderRunner` does internally, minus the broken jar.
- `TeaVMTool.setClassPath()` is the classpath TeaVM uses to resolve BOTH your own classes AND its own `java.lang.*`/`org.teavm.runtime.*` support classes — it does not fall back to the driver's own JVM classpath. Needs teavm-classlib + teavm-interop + teavm-platform + teavm-core jars in there, not just teavm-classlib.
- **`setMinHeapSize(int)`/`setMaxHeapSize(int)` take raw BYTES**, despite teavm-cli's own `--min-heap`/`--max-heap` help text saying "in megabytes" (that CLI just forwards the parsed int with no `*1024*1024`). Passing small ints like (4, 32) reserves/commits an almost-nonexistent heap; nothing fails at the call site — it segfaults much later, on the first actual GC write inside `meth_otr_GC__clinit_()`, which looks completely unrelated unless you know to suspect it. Pass real byte counts (e.g. 4*1024*1024 / 32*1024*1024).

## Compiling the generated C with llvm-mingw's clang
- **Since 2026-10-09 (jr PRP-37) these patches live in a TeaVM fork instead of a post-processing script: `jarrunner/teavm`, branch `0.16.0-jr`, artifacts `io.github.jarrunner.teavm:*:0.16.0-jr.1` (see `JARRUNNER.md` there). Depend on that rather than writing a new patch script.** TeaVM 0.16.0 itself fixed the macOS gaps (no `uchar.h`, no POSIX timers in `fiber.c`). Headers for your own `@Import` calls belong in `@org.teavm.interop.c.Include` on the binding class (jextract_teavm `--include`), never forced into `definitions.h`; name the header so no Java class shares it (on Windows `jr.h` finds TeaVM's `Jr.h`) and give it `#pragma once`. The list below records what each fix is and why.
- **Required patches to the generated tree before it will compile** (all four confirmed by actually hitting the error, not preemptive) — automate with a script like jr's `postprocess.ps1`, don't hand-edit:
  1. Do NOT pass `-I.` to clang — unlike tcc, clang already searches the including file's own directory for quoted includes per the C standard; passing `-I.` anyway makes generated `uchar.h`'s own `#include <uchar.h>` shadow itself.
  2. `definitions.h` misclassifies clang-targeting-mingw as `TEAVM_UNIX`, because it picks `TEAVM_WINDOWS` only under `_MSC_VER` and `TEAVM_UNIX` under any `__GNUC__` — and mingw compilers (clang included) define `__GNUC__` for source compatibility even though the real target is Windows. Wrong branch pulls in genuine POSIX-only APIs (`timer_create`, `SIGRTMIN`, `sigaction`, `strptime`, `timegm`) that don't exist under mingw — real compile errors. Fix: check `__MINGW32__` before falling through to bare `__GNUC__`. The `TEAVM_WINDOWS` branch (real Win32 APIs) already exists in fiber.c/date.c and works once routed to correctly.
  3. `__assume(0)` (MSVC's optimizer-hint intrinsic, used as `TEAVM_UNREACHABLE` in the `TEAVM_WINDOWS` branch) doesn't exist under clang. Fix: `#define __assume(x) __builtin_assume(x)`, scoped to `__MINGW32__ && !_MSC_VER` so real MSVC keeps its real intrinsic.
  4. mingw's own `<uchar.h>` only declares `mbrtoc16`/`c16rtomb` under `#ifdef _UCRT` — the msvcrt target never had these two C11 string-conversion functions. TeaVM already ships a rough-conversion fallback for `TEAVM_PSP` (a platform with no real libc); widen its guard to `TEAVM_PSP || (TEAVM_WINDOWS && !defined(_UCRT))` and reuse it.
- **`Runtime.getRuntime().exit(int)` / `System.exit(int)` are silent no-ops in TeaVM's C-backend classlib** (`System.exit` itself is flatly unimplemented and throws `{{m0}} was not found` if called; `Runtime.exit` compiles but just returns, code after it keeps running, and the OS-visible exit code is always whatever the auto-generated `main()` hardcodes). **Bind directly to libc's real `exit()` via `@Import` instead**: `@Import(name = "exit") private static native void cExit(int code);` — confirmed to actually terminate the process and set the real exit code.
- **Any WinAPI (not CRT) function called via `@Import` needs `-include windows.h` on the compile line.** `@Import` only emits the bare call — it doesn't know the symbol needs a header, so the generated code calls it as an implicit (K&R-style) declaration at first use. In a single-translation-unit `all.c` build, TeaVM's own file ordering can place your class's generated `.c` (with the `@Import` call) BEFORE `core.c` (whose `#include <Windows.h>`, needed for the `TEAVM_WINDOWS` runtime, would otherwise declare it first) — so the compiler builds an implicit declaration, then hits `error: conflicting types for 'GetConsoleWindow'` etc. once the real prototype shows up later in the same TU. `-include windows.h` forces the real header to be seen before anything else in the TU regardless of internal include order. CRT functions (`exit`, `system`, `getenv`) don't need this — they're already declared via `<stdlib.h>` early in TeaVM's own header chain.
- **Size-optimized release build**: `-Oz -flto -ffunction-sections -fdata-sections -Wl,--gc-sections -s`. tcc doesn't do dead-code elimination at all (moot here since tcc doesn't work), but plain `-O2` alone also leaves a lot of unused GC/runtime on the table — the `--gc-sections` family made roughly a 4x difference in jr's own measurements (hello-world: ~412KB at `-O2` down to ~110KB with the full flag set).

## NEVER store org.teavm.interop.Address values in a regular Object[] array (CONFIRMED CRASH, not theoretical)
`Address` is a raw-pointer intrinsic on TeaVM's C backend, not a real heap object - it compiles down to a plain `void*`. Declaring `private static final Address[] SAVED = new Address[3]` and writing `SAVED[i] = someHandle` compiles cleanly and runs for a while, then **segfaults later, inside seemingly unrelated code**, with zero compiler warning anywhere. This is exactly the kind of bug that eats hours: everything up to and including the array write succeeds silently, and the actual crash is not at the write but downstream (in this case, inside the very save/restore routine that used the array, jr's port hit it precisely at `saveStdHandles()`/`GetConsoleMode` calls that immediately followed writing three `Address` values into an array).
**Fix: never index an `Address`. Use separate named fields instead** (`Address saved0, saved1, saved2;`), or a raw `byte[]`/`Address.ofData(byte[])` buffer read/written via `.add(offset).getLong()`/`.putLong()` if you genuinely need N of them and N is more than a handful. The same caution applies to any other TeaVM interop intrinsic type (`Address`, `Function` subtypes, `Structure` subtypes) - don't put them in ordinary Java collections or arrays; TeaVM's GC/array machinery is built for real heap objects and primitives, and these intrinsics are neither.
**Generics and Optional are the same trap, measured 2026-10-08 (jr PRP-35 phase 8).** `Optional<Address>` (and so any `List<Address>`, `Map<..., Address>`, anything that keeps an `Address` in an `Object` slot) segfaulted as soon as the Optional really existed across a GC (kept in a static field, 1000 of them, then a 25 MB allocation loop); the identical program with `Optional<Long>` holding `toLong()` ran fine. A quick test with a local `Optional` "works" only because TeaVM inlines the Optional away entirely (`q = p` in the C), so a passing micro-test proves nothing. For "maybe a pointer" use a compile-time check instead (teavm_native_check NC10 `@Fails`, which costs nothing at run time), and if a value must be boxed, box `toLong()`. teavm_native_check reports a pointer type argument as NC2-generic.
Diagnosing this took bisection via inserted `fprintf(stderr, ...)`/`fflush(stderr)` checkpoints directly into the GENERATED `.c` file (not the Java source - the generated code is what's actually crashing, and it's plain readable C) - a binary-search of checkpoint insertions across the class-init sequence, then into the specific method, narrowed it to one specific native-call sequence in under 10 minutes. Reach for this technique whenever a TeaVM+C-backend program segfaults with no compiler diagnostic: insert cheap stderr checkpoints in the generated code (not gdb - a debugger's symbol names are TeaVM's own mangled ones, less useful than just reading the readable-if-verbose generated C directly) and bisect.

## Structs / WinAPI calls needing STARTUPINFOA-style marshaling
Don't bother with `org.teavm.interop.Structure` for WinAPI structs — it's more trouble than it's worth here (see the function-pointer note below for why `Structure` specifically gets in the way). Instead: allocate a plain `byte[]` sized to the real struct's byte length (compute the x64 layout by hand — fields are laid out in declaration order with standard C alignment, e.g. an 8-byte pointer field after a 4-byte DWORD gets 4 bytes of padding first), get its `Address` via `Address.ofData(byte[])`, and read/write individual fields with `address.add(offset).getInt()/putInt()/getLong()/putLong()` etc. at the byte offsets you computed. This is lower-risk than it sounds because Win32 struct layouts are stable, extensively documented ABI, not something to reverse-engineer — just look up the field list and compute offsets carefully once.

## Calling a runtime-obtained function pointer (GetProcAddress) — CONFIRMED WORKING
This is the mechanism a real jli.dll-style in-process JVM launch needs (or any WinAPI callback-table pattern), and it is NOT obvious from TeaVM's own API surface. Verified end-to-end 2026-09-11 (`pocapp.FnPtrTest` in jr's teavm-poc, calling msvcrt's `abs()` via `LoadLibraryA`+`GetProcAddress`).
1. Declare an abstract class extending `org.teavm.interop.Function` with ONE abstract instance method matching the target C signature: `public abstract class MyFn extends Function { public abstract int invoke(int x); }`. The C backend recognizes ANY class transitively extending `Function` (`Characteristics.isFunction`, pure superclass-chain check) and compiles a call on it to a raw C function-pointer cast-and-call: `(((RetType (*)(ArgTypes...)) value)(args...))`.
2. **Do NOT use `Address.toStructure()` to get there** — its real signature is `<T extends Structure> T toStructure()`, so it flatly refuses a `Function` subtype at compile time (`incompatible upper bounds ...,Structure` — this is what happens if you try, don't waste time debugging it further, just avoid it).
3. **The actual working move: a raw unchecked cast through `Object`** — `MyFn fn = (MyFn) (Object) someAddress;`. This compiles (an unrelated-reference-type cast through `Object` is always syntactically legal in Java, checked at runtime on a real JVM) and, on TeaVM's low-level model, these opaque intrinsic-backed types skip any real instanceof machinery — inspecting the generated C confirms the Address value flows straight through into the function-pointer-cast-and-call with no runtime check at all. Confirmed correct at actual runtime, not just "it compiled."
4. `LoadLibraryA`/`GetProcAddress` are themselves ordinary `@Import`-bound WinAPI calls (`Address`-typed params/return) — nothing special needed for those two.

## Beyond windows.h: any extra WinAPI subsystem header needs the SAME definitions.h treatment
`windows.h` alone does NOT declare WinHTTP, BCrypt/CNG, or the common-controls (Progress Bar etc.) APIs - those live in separate SDK headers (`winhttp.h`, `bcrypt.h`, `commctrl.h`) that windows.h does not pull in by default. The exact same reasoning and the exact same fix as the windows.h/time.h patch in postprocess.ps1 applies: add `#include <winhttp.h>` / `#include <bcrypt.h>` / `#include <commctrl.h>` (angle-bracket, so it resolves via the system include path, not the generated tree) to the SAME insertion point at the top of `definitions.h`, before `core.h`'s own include chain runs. Forgetting this produces `error: call to undeclared function 'WinHttpOpen'` (etc.) plus `incompatible integer to pointer conversion` on ITS return value, since an implicit K&R-style declaration assumes `int`, not `HINTERNET`. Found and fixed 2026-09-13 (jr PRP-09, java auto-install feature) - see jr's `postprocess.ps1` for the actual patched list.

## WPARAM / LPARAM / DWORD_PTR / LRESULT are INTEGER typedefs on this toolchain's headers, not pointers - declare them `long`, never `Address`
Despite being "pointer-sized" and often used to smuggle a pointer, llvm-mingw's SDK headers define `WPARAM`/`LPARAM` as `UINT_PTR`/`LONG_PTR` -> plain `unsigned long long`/`long long`, and `DWORD_PTR` likewise - NOT `void*`. Declaring a `@Import` parameter of this kind as `Address` and passing `Address.fromInt(0)` (or any Address) compiles fine on ITS OWN, but as soon as the real header is in scope (see above) clang flags every call site: `incompatible pointer to integer conversion passing 'void *' to parameter of type 'WPARAM' (aka 'unsigned long long')` - a hard error, not a warning. Hit this on `SendMessageA`'s `wParam`/`lParam` and `WinHttpSendRequest`'s `dwContext`. **Fix: declare these params (and matching return types like `LRESULT`) as plain Java `long`, and pass plain numeric literals** (`0L`, a computed `long` percent, `MAKELPARAM`-style bit-packed constants like `0x00640000L`) instead of wrapping them in `Address.fromInt(...)`. Genuine pointer-typed WinAPI params (`HWND`, `HANDLE`, `LPVOID`, `LPCWSTR`, etc.) stay `Address` as everywhere else in this port - this is specifically about the handful of Win32 types that are pointer-*sized* integers, not pointers.

## A GUI window/dialog frame does NOT need a custom-registered window class or a WNDPROC callback
Building a small always-on-top progress window (or any simple modeless UI) from TeaVM does not require solving "how does native code call back into a Java method" (which this port has no established mechanism for at all - the `Function`/`GetProcAddress` technique above is Java-calling-native, not the reverse). Create the top-level frame as a plain window of the **pre-registered system class `"#32770"`** (the built-in Windows dialog class - `CreateWindowExA` with that class name and no prior `RegisterClassA`/`WNDCLASSA` at all) instead of registering a custom class. It comes with a working default window procedure (`DefDlgProc`) for free. Add ordinary pre-registered child controls the same way (`"STATIC"` for a label, `"msctls_progress32"` for a progress bar after one `InitCommonControlsEx(ICC_PROGRESS_CLASS)` call) - `hInstance` can be `NULL`/`Address.fromInt(0)` throughout since none of these are app-registered classes. Pump the message queue with an ordinary `PeekMessageA`/`TranslateMessage`/`DispatchMessageA` loop on a `MSG` buffer (add `MSG` to `winstructs.toml` and regenerate via OffsetGen - see PRP-08 - rather than hand-computing its padding; verified `SIZE=48` on x64, not the naively-guessed 40/44). Confirmed working end-to-end 2026-09-13 (jr PRP-09's install-progress window) - real window, no custom class, no callback-into-Java needed.

## BCrypt property-name string constants: verify against the REAL header, not memory - `BCRYPT_HASH_LENGTH` is `"HashDigestLength"`, NOT `"HashLength"`
When binding a `#define SOME_NAME L"literal"` style WinAPI constant (common in bcrypt.h and friends) by hand-typing the wide string into `Wstr.of("...")`, the macro NAME is not a reliable guide to its STRING VALUE - `BCRYPT_HASH_LENGTH`'s own literal is `"HashDigestLength"`, not the "HashLength" one line of reasoning (and most blog-post sample code) would suggest by analogy with the sibling `BCRYPT_OBJECT_LENGTH` = `"ObjectLength"`. Passing the wrong-but-plausible string doesn't fail loudly: `BCryptGetProperty` returns `STATUS_INFO_LENGTH_MISMATCH` (0xC0000004), which reads like a buffer-size bug, not a wrong-property-name bug, and the output buffer is left untouched (silently keeping whatever the PREVIOUS successful call wrote there, making it look even more like a real value at a glance). **When a property/constant lookup fails with a "length" or "not found" style status, write a five-line throwaway C program with the SAME toolchain (`#include <bcrypt.h>`; `printf("%ls", BCRYPT_HASH_LENGTH)`) and print the macro's actual expansion, rather than trusting recollection of "the sample code I've seen."** This is the same discipline PRP-08's whole offsetof-probe exists for, just applied to a string constant instead of a struct offset. Found and fixed 2026-09-13 (jr PRP-09's SHA-256 checksum verification).

## A static `Address` constant can read 0 - its class initializer has not run yet (CONFIRMED)
`public static final Address X = Address.fromLong(...)` is not a compile-time constant; it is set in the class's static initializer, and a read does not always trigger that initializer first. Measured in jr (PRP-24, 2026-09-29): `WinApi.RT_RCDATA` (a generated `Address.fromLong(10L)`) read **0** inside a method that had just called a `WinApi` `@Import` native. The same field read 10 later in the run, and read correctly when touched as the first statement of `main`. Likely mechanism: TeaVM skips the class-init check on a field read when the same method already called a static method of that class, assuming the call initialized the class, but `@Import` natives never run it. **Nothing fails: the 0 goes straight into the native call.** Here that was `FindResourceExW` asking for resource type 0, returning NULL, and looking exactly like "the resource isn't there". It took three wrong hypotheses (live module handle, language id, hand-built name address) before a one-line trace of the constant's value showed it. **Rules:** touch the constants holder (read one of its `Address` fields) as the first statement of `main`, before anything else calls into it; when a native call "can't find" something you can prove exists, print the constant values you passed before theorizing about the API. Primitive constants (`static final int`) are inlined by javac and are immune. The durable fix is in a bindings generator like jextract_teavm: emit pointer-typed constants so they don't depend on class initialization.

## `System.err` output may arrive on stdout
Measured on jr's llvm-mingw build: `System.err.println` output landed in the redirected stdout file, and the stderr file was empty. Don't design a diagnostic around separating the two streams. Write traces to a file (jr has `Dbg`, gated by `JR_DEBUG=1`). Grepping multi-line trace output also silently drops the continuation lines; that hid a working result during the same investigation.

## `Address.add()` is `char*` in the generated C, every other Address is `void*` (CONFIRMED, patched in jr)
TeaVM 0.15.0's core.h: `#define TEAVM_ADDRESS_ADD(address, offset) ((char *) (address) + (offset))`. C converts `void*` to any pointer type implicitly, `char*` it does not. So `someImport(ptr.add(n))` compiles when the parameter is `void*`/`LPVOID`, or when the call goes through a `Function` pointer cast (no prototype), and FAILS when the parameter is a typed struct pointer: `CreateFontIndirectW(ncm.add(408))` gave "incompatible pointer types passing 'char *' to parameter of type 'const LOGFONTW *'", an error by default from clang 16. It hides for a long time because most WinAPI pointer parameters are `void*`-ish. **Fix at the root, not per call site:** patch the macro to `((void *) ((char *) (address) + (offset)))` in the build's post-processing step (jr: `postprocess.ps1`, PRP-31). Reported as a TeaVM upstream candidate (jr prp/15-prp.01, item 11).

## A TeaVM-built Windows exe that shows windows needs an application manifest
Without one, Windows treats the exe as legacy: on a scaled display (125%, 150%) its windows are bitmap-stretched (blurry, "compatibility mode" look), and controls get the Windows 95 style. Declare what java.exe's own manifest declares: a dependency on Microsoft.Windows.Common-Controls 6.0.0.0, `dpiAware` `true/PM` plus `dpiAwareness` `PerMonitorV2, PerMonitor, system`, and supportedOS. For a launcher hosting a JVM in-process this also matters for the app: its Swing/JavaFX windows inherit the process's DPI awareness. Then use the system message font (`SystemParametersInfoW(SPI_GETNONCLIENTMETRICS)` -> `lfMessageFont` -> `CreateFontIndirectW`), not `DEFAULT_GUI_FONT` (an old bitmap-era font), and scale every hard-coded coordinate by `GetDeviceCaps(LOGPIXELSY) / 96`. jr PRP-31, 2026-10-03.

## Never @Import a function that exists only in Common Controls 6 (or any newer DLL version) - look it up at run time
`LoadIconWithScaleDown` (and other comctl32 v6-only exports such as `TaskDialogIndirect`) is in comctl32 v6 only. An exe whose manifest does not ask for v6 - and a freshly linked exe has NO manifest until a later stamping step adds one - gets comctl32 v5, so a static import makes the exe fail to START: "Entry Point Not Found" dialog, exit code 0xC0000139 (STATUS_ENTRYPOINT_NOT_FOUND). In jr this broke the build itself (the new exe is the resource-stamping tool) and a user double-clicked the broken copy. Resolve such functions with `GetModuleHandleA("comctl32.dll")` + `GetProcAddress` and a hand-written `Function` subclass, with a fallback (jr: `WinIcons` falls back to `ExtractIconExW`). Same rule as `IsWow64Process2`. For the caption icon: `LoadIconWithScaleDown` at `GetSystemMetrics(SM_CXSMICON)` downscales a single 256x256 entry smoothly, where `ExtractIconExW`'s own small icon is visibly pixelated. jr PRP-31, 2026-10-03.

## Threads on the C target: green threads only, and managed code never on a second OS thread (measured 2026-10-08, jr PRP-33)
- `java.lang.Thread` works as cooperative fibers on ONE OS thread (`TThread.start()` -> `EventQueue.offer(Fiber.start(...))` for low-level targets). Tested through jr's pipeline: sleep-interleaving, `join`, `synchronized`, `wait`/`notifyAll` work; a thread computing 300 ms without waiting is not preempted; a blocking native call blocks every fiber. Cost: about +50 KB (146,944 vs 95,744 bytes, -Oz).
- **Build gotcha:** `Object.wait/notify` makes TeaVM need `teavm-jso` and `teavm-jso-apis` on the classpath even for C (`Object$NotifyListenerImpl implements org.teavm.jso.browser.TimerHandler`), otherwise "Class ... implements ..., which is missing in the classpath".
- **Never run managed Java on another OS thread** (a `Function` callback from `CreateThread`, a thread-pool, a console Ctrl handler, an async-I/O completion): the runtime has no locks and no thread-locals, and `teavm_stackTop` (the shadow stack the GC scans) is a single global in `stack.c`. A callback from another thread is tolerable only while the main thread is provably blocked in native code (jr's atexit hook in jvm=dll mode is such a case). `org.teavm.interop.@Unmanaged` exists for methods without GC bookkeeping; how strictly TeaVM enforces it is not verified.
- Any shared bump/arena allocator (like jr's `N`/`Arena`) breaks if two fibers interleave scopes: don't suspend (sleep/wait/join) inside a scope.
- **Native memory safety is checked at compile time, not by review (jr PRP-35, 2026-10-08).** Use `../../jarrunner/teavm-native-check` (repo jarrunner/teavm-native-check, on Maven Central as `io.github.jarrunner:teavm-native-check`) (javac plugin, `-Xplugin:NativeCheck ...`, compile time only) and generate bindings with `jextract_teavm`'s `--ctype-annotation`, `--text-converter`/`--text-scope` (String overloads that convert and free), `--buf-class`, `--returned-annotation`, `--escapes-annotation`. The worked setup and the rules for writing native calls are in jr's `jr/jr/README.md`, section "Native memory"; read it before writing new `Address` code in any TeaVM C project.
- **Size costs in the C backend, measured in jr (PRP-35, 2026-10-08):** `try/finally` (and `try/catch`) is built on `setjmp` (`TEAVM_TRY`, volatile spills, an exception path): about 400 bytes per method in the optimized exe, plus a `setjmp` per call. Around a native call, which cannot throw a Java exception, write the cleanup as plain sequential code instead (jr's generated String overloads: 30 wrappers went from +12.8 KB to +3 KB this way). Every lambda is its own class, about 1.5-3 KB of generated C. Tiny static helpers are not inlined.
- **The Java heap is fixed at build time** (jr: 32 MB max in BuildDriver). A large file read into a `byte[]` crashes with "Application crashed due to lack of free memory"; keep big payloads in native memory (jr reads raw resources off-heap at the native call).
